# 0086 — Scoped workspace preference replay

Status: implementation beginning, 2026-10-13.

Existing LocalRuntime already captures original calendar.settings, navigation.save
and navigation.move intent. Reuse it, not a second command store. Calendar is the
workspace singleton with entity ID workspace on both adapters. Navigation is a
principal-owned singleton; local installation principal and authenticated remote
principal are different namespaces and must never be conflated.

Implement calendar replay first through ordinary WorkService, a complete single
calendarSettings UPSERT guard and existing authenticated business/receipt
transaction. Preserve ordinary Activity/Outbox generated by the service, while
rejecting other business writes. No direct adapter mutation or Domain copy.

Calendar canonical value remains exactly version/timezone, without fabricated
business id/workspace properties. Metadata delta values are validated against
their journal record; calendarTimezone is a derived companion, not another entity.
Canonical ACK and cursor projection reuse existing scope/revision/base/attempt
guards and retain later pending local edits. No SQLite/PostgreSQL migration.

Navigation requires explicit authenticated principal mapping, receipt/base identity
mapping and account-specific delta validation before enabling replay; do not send
the installation owner ID as a remote target or accept another user's preference.
Other unsupported families must continue stopping unsafe cursor advancement.

Verify real SQL/PostgreSQL transaction parity, original bytes, duplicates, stale
versions, undeclared-write rollback, timezone/canonical value validation and real
Host/IndexedDB coordinator restart. Explicit first binding/merge preview/rebase/
conflict UI and FINAL notification/other phases remain separate unfinished gates.

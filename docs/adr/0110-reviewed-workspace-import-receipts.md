# ADR0110 — Reviewed import revisions and recoverable step receipts

2026-10-15. FINAL Phase11–13 requires explicit reviewed destination state, original portable backup, additive formal Application mutations and recovery without rebinding a nonempty source.

An optional X-Workspace-Precondition JSON header carries exactly epoch and cursor on supported business mutations. Adapters detach the receipt before awaiting, check authenticated membership/session authorization, look up an existing receipt, then validate the destination head inside the existing workspace transaction/lock before business writes. A stale head fails without entity/Activity/Outbox/receipt changes. The guard contributes to the receipt digest; an uncertain successful retry returns its exact recorded response despite subsequent remote mutations, while changing a guard under the same key fails. Requests without guards preserve historical receipt digests.

Guarded responses wrap the ordinary result with workspaceRevision captured within that same transaction and stored with the receipt. Browser and native UTF-8 JSON transports preserve the optional guard and explicit workspace scope. No Rust business rules or raw database import endpoint are introduced. SQLite/PostgreSQL use existing receipt storage; historical migrations remain unchanged.

A durable local import journal will retain immutable backup/identity/reference decisions and stable per-step IDs/payloads. Each accepted step advances its recorded destination head by compare-and-swap; failed local checkpointing retries the identical server receipt. No source Outbox is cleared and no source binding is changed merely because some remote writes succeeded. Completion and replica activation remain separate, validated operations.


Reviewed manual-order import uses an explicit sequence of entity IDs plus the destination scope version, not copied position rows. The Application service validates the entire sequence and membership before any move, then reuses normal move rules under a single UnitOfWork transaction. Existing destination members keep relative order; selected imported members are appended in their source order. A guarded, human-only Host route receipts this operation atomically. The immutable import plan captures the reviewed target aggregate version. No historical migration or new order ownership model is introduced.


Before forking a stale import review, uncertain effects must be reconciled by authenticated read-only receipt lookup. This uses a separate reviewed-receipt proof (exact canonical guarded digest: original path/body SHA256 plus epoch/cursor), scoped to workspace/principal and command UUID. It does not relax ordinary device-scoped receipt lookup or expose legacy/no-device receipts. Malformed proof is rejected; missing, unrelated and wrong-proof receipts are indistinguishable. No receipt or business write occurs on lookup. A fork retains immutable parent/version lineage and a fresh verified source backup at the newly reviewed destination head; it never rewrites the previous journal.

Changed final Work state and File rename operations require an explicit local/destination decision. A child stores the exact detached destination entity/version and decision as immutable reviewedChanges evidence. The Application resolver permits only importer's final status/activation/lifecycle fields or File name; identity, original binary, source reference, relationships and unrelated remote fields cannot be amended through this mechanism. Fork creation recomputes the permitted suffix from parent plus evidence inside its existing local transaction. The runtime separately verifies evidence against a fresh manifest at the reviewed epoch/cursor, then creates the new backup/fork. Preparation does not execute it. Formal guarded Application mutations still perform domain, permission and version checks on explicit Resume. Missing/deleted entities, create collisions and unsupported structural conflicts remain blocked rather than silently accepting a choice.

Manual-order review uses that same immutable evidence and canonical Domain aggregate validation. LOCAL retains the imported selected sequence at the fresh aggregate version; REMOTE preserves every recorded destination entry's relative order and appends only missing imported IDs. Normal scope membership validation still occurs in the formal Application transaction. Following an explicitly resolved Work update, later organization entries may carry forward only its deterministically resulting business version; archive/folder/tag intent and organization aggregate versions are unchanged. A separately changed organization remains a conflict. Project finalization sends lifecycle alone because the Application contract prohibits task activation fields on Projects.

Owned Space/Document import composes existing ProjectService stable creation commands. A copied material must pair with a copied library target; reuse of an existing remote target as owned is rejected before execution. Creation atomically receipts both material and library effects, followed by an ordinary versioned library save restoring original Markdown, hierarchy, Document aliases and policy. Dependencies include owner Project, linked/owned Space binding and parent Document. Linked Documents reuse ProjectService.link via the same stable-ID wrapper used by other knowledge commands; optional replay metadata is human-only, documented on both REST aliases, and existing authorization/duplicate/target checks remain unchanged. No raw material insertion or ownership conversion endpoint is added.

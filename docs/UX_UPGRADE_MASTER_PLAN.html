OrivaneAtlas 全面 UX、品牌与产品体验升级实施总纲

项目：OrivaneAtlas
目标：在保留既有业务能力、数据安全与兼容性的前提下，完成全产品范围的品牌重塑、设计系统升级、信息架构优化、交互重构、资源中心重做、各功能模块体验升级，以及对应的工程质量和发布验收。
执行对象：具备仓库读写、终端、测试和必要浏览器/桌面验证能力的工程 Agent。
本文是完整目标和执行契约，不是某一个 Sprint 的局部任务单。

0. 最终任务定义

你受托完成 OrivaneAtlas 的全产品体验升级，不是只做文件库，不是只换主题，不是只产出设计稿，也不是只提交一份建议。

最终需要交付一个可构建、可运行、经过测试、具备迁移与回滚方案的产品版本，至少覆盖：

  1. 全新品牌视觉系统：品牌定位表达、Logo/图标资产策略、色彩、字体、图标、插画、动效和跨平台品牌一致性。
  2. 完整 Design System：设计 Token、基础组件、复合组件、页面布局模式、交互状态、无障碍和响应式规则。
  3. 全局应用 Shell：侧边栏、顶栏、导航、页面标题、搜索、命令面板、通知、同步状态、浮层和移动导航。
  4. 文件库 / 资源中心：重新设计信息架构、统一资源浏览、文件夹体验、搜索筛选、列表/网格、预览、详情、上传、批量操作、关联关系与回收站体验。
  5. 笔记、日记、文档、知识空间、项目、任务、日历、图谱、AI Assistant、账户/设置、通知等所有主要模块的体验一致性升级。
  6. Web、Windows/Tauri、Android 等现有目标平台的适配和行为一致性。
  7. 前端结构、样式组织、状态管理、性能、测试和文档的配套升级。
  8. 生产运维体验：同步状态可理解、错误可恢复、备份恢复说明准确、发布与迁移安全。
  9. 完整验收报告：问题、决策、变更、测试证据、未完成项、已知限制、发布与回滚步骤。

允许分阶段实施、允许 Agent 因上下文、时间、工具或安全原因暂停并报告；不允许把最终目标缩小成一个局部模块，不允许将”阶段性报告”冒充最终交付。 每次暂停必须保存状态，说明已完成、未完成、阻塞原因、证据和下一步。后续继续时必须从检查点恢复，直到全目标完成或明确报告客观无法完成的阻塞。

2. 不可违反的工程约束

2.1 数据安全与兼容

  • 不删除、重建、清空或覆盖任何用户数据库、真实用户缓存、未跟踪文件、生产文件或密钥。
  • 不执行 git reset --hard、git clean、危险数据库重置、未经批准的生产迁移或发布。
  • 不将真实用户数据用于测试；测试必须使用隔离 fixture / 临时数据库 / 独立 profile。
  • 数据迁移必须可审查、具备迁移前备份建议、迁移后校验和明确回滚策略。不可逆迁移必须标注，并提供安全恢复路径。
  • 保持 Workspace / Principal / Actor / 私有资源的授权边界。任何统一资源查询必须在服务端或可信 Application 边界做权限过滤，不能只靠前端隐藏。
  • 不绕过 CAS、版本检查、Revision、UnitOfWork、事务、Outbox/ACK、Mutation Receipt、幂等键或冲突审查。
  • 文件元数据与二进制内容必须保持一致性；上传、恢复、删除、清理都要考虑失败和重试。
  • 旧数据、旧客户端、已有用户主题偏好和 URL 深链应尽量兼容。破坏性变更必须给出迁移与兼容方案。

2.2 架构边界

  • 保持并强化 UI → Application → Domain / Ports → Adapters 依赖方向。
  • UI 不直接执行 SQL、不调用 Provider SDK、不实现授权判定、不拼装跨权限资源事实。
  • 不为了”现代架构”盲目引入微服务、事件总线、状态管理框架或新数据库。
  • 优先 Modular Monolith、Feature-oriented Frontend、明确的 Query/Command、可测试的 Application Service。
  • 仅在真实痛点和测量证据支持时引入 CQRS、虚拟列表、缓存、Worker、异步任务等机制。
  • 新依赖必须说明必要性、维护成本、许可证、包体积和替代方案。
  • 不以大量防御性抽象、重复状态、无意义 wrapper 或只为测试样式而制造复杂度。

2.3 UI/UX 原则

  • 方向为 C：现代编辑型 + 专业工作台。整体柔和、清晰、内容优先；复杂场景保留专业密度和高效操作。
  • 品牌视觉系统整体重新设计，不强制保留旧紫色作为主品牌色；品牌决策需通过完整方案统一，不可每个模块自行选色。
  • 不复制 Claude、Notion、Linear、Craft 等产品的品牌或具体界面；可以学习通用交互范式。
  • 设计必须覆盖 Light / Dark、桌面、窄屏、移动端、键盘操作、Focus、Hover、Disabled、Loading、Empty、Error、Success 等状态。
  • 避免大面积纯白/纯黑、过度卡片套卡片、过量胶囊、过重阴影、无意义渐变、全屏玻璃、过度动画和视觉噪音。
  • 动效遵守 prefers-reduced-motion；颜色满足 WCAG 2.2 AA 对比度目标；交互目标尺寸考虑触控。
  • 不可仅凭截图美化；必须验证真实任务流程和大量数据场景。

4. 全新品牌系统与 Design System

4.1 品牌设计交付

形成完整品牌规范，至少包括：

  • 品牌定位、设计关键词、视觉原则、语气与命名。
  • 主标志、横向字标、图形标、应用图标、favicon、通知图标。
  • 图标在 16/20/24/32/48/64/128/256px 的可识别性。
  • Windows、Android、Web、Tauri 原生资源一致性。
  • 中文和英文的字体栈、字号、字重、行高、字距。
  • 主色、辅助色、强调色、语义色、浅色/深色主题。
  • 空状态插画、引导图、资源类型图标、状态图标规范。
  • 品牌动效与过渡规范。
  • 不同背景、尺寸、明暗模式下的 Logo 使用规则。

不要把本文件中的概念色值当成已批准最终色板。Agent 应提交至少两套有明确差异的品牌方案，基于真实 UI 组件制作应用场景对比，选择一套并说明理由。若用户没有参与即时确认，采用最符合已确认方向 C 的方案，记录决策，不得无限等待确认。

4.2 Token 架构

建立单一事实来源，建议分层：

  • Primitive tokens：基础色阶、字号、间距、圆角、阴影、动效时长。
  • Semantic tokens：canvas、surface、text、border、accent、success、warning、danger、focus。
  • Component tokens：按钮、输入、导航、列表、弹窗、菜单、卡片。
  • Density tokens：comfortable / compact。
  • Platform tokens：desktop / narrow / touch。
  • Theme tokens：light / dark。

所有组件优先使用语义 Token。禁止新代码直接硬编码设计颜色、圆角、阴影和尺寸，少量不可避免的图表/图片/品牌资源除外。逐步清理旧 CSS，但不可用一次性全局替换造成回归。

4.3 组件系统

统一基础组件：

  • Button / IconButton / SplitButton
  • TextField / SearchField / Textarea / Select / Combobox
  • Checkbox / Radio / Switch / SegmentedControl
  • Tabs / Breadcrumbs / Pagination
  • Tooltip / Popover / Dropdown / ContextMenu
  • Dialog / Drawer / CommandMenu
  • Toast / InlineNotice / Progress / Skeleton
  • ListRow / ResourceRow / Card / EmptyState
  • Sidebar / PageHeader / Toolbar / SplitPane / Inspector
  • Dropzone / UploadQueue / PreviewHost

组件必须有完整状态、键盘行为、ARIA 语义、焦点管理和测试。避免将业务逻辑塞入通用组件。

4.4 全局布局模式

建立统一：

  • Application Shell
  • Global Navigation
  • Page Header
  • Search / Command Surface
  • Content Container
  • Split View
  • Inspector Panel
  • Responsive Drawer
  • Empty / Loading / Error layouts

各页面可以有差异，但不能各自重新发明导航、标题、间距和浮层行为。

5. 全产品模块升级范围

必须逐个审查并完成以下模块，而不是只升级文件库：

5.1 全局 Shell 与导航

  • 侧边栏层级、分组、选中状态、折叠态、工具提示。
  • 顶栏高度、搜索、新建、通知和同步状态布局。
  • 页面标题、面包屑、主操作位置。
  • Command Palette 与快捷键。
  • 移动端导航和窄屏抽屉。
  • 导航排序/固定行为。
  • 避免无意义计数和重复操作入口。

5.2 Dashboard / 总览

  • 展示真正可行动的信息，而非装饰性统计。
  • 今日任务、近期项目、最近资源、待处理事项。
  • 信息优先级清晰，模块可收敛，空状态有引导。
  • 首屏内容密度适中，加载分区化。

5.3 文件库 / 资源中心（重点模块）

目标：成为统一、可扩展、可理解的资源管理入口。

信息架构

建议资源中心入口包含：

  • 全部资源
  • 最近访问
  • 收藏
  • 我的文件夹
  • 项目资源
  • 回收站

同时保持笔记、日记、知识空间原有专门工作流，不强迫用户只能从资源中心进入内容。

浏览器布局

  • 桌面宽屏：可调节三栏（目录 / 资源 / Inspector）。
  • 常规桌面：目录 + 资源，详情抽屉或可关闭 Inspector。
  • 窄屏：单栏，目录和详情作为 Drawer。
  • 移动端：全屏导航层或底部/侧边抽屉，触控目标适配。
  • 左侧目录支持树形层级、折叠、创建、重命名、移动、拖放排序、键盘操作。
  • 中间资源支持列表/网格、面包屑、筛选、排序、多选、批量操作。
  • 右侧 Inspector 支持元数据、预览、位置、项目/Space 关联、操作。
  • 列宽、面板开关、布局偏好可持久化，但不可污染跨账户/工作区状态。

资源类型

统一浏览 Note、Document、File，但不把它们错误地压成同一个数据库实体。通过类型安全的 ResourceRef / View Model 统一展示：

  • 类型、标题、图标、更新时间、创建时间、位置、大小、MIME、关联项目/空间、可用操作。
  • 每种类型仍调用其正确的 Application Service 和权限路径。
  • 搜索、筛选和排序的语义一致；无效筛选、空结果、权限拒绝必须有明确反馈。

文件夹与关系

  • 先检查现有 FolderLink、SpaceFolderLink、ProjectFolderLink、Note primary folder 和 Document/File 归属语义。
  • 评估是否支持通用资源关联、多文件夹引用、主要归属位置、项目/Space 关联。
  • 先实现统一读取投影和 UX，再决定是否改数据库。
  • 如需 Schema 变更，编写 ADR、迁移、数据回填、权限检查、同步 replay、回滚/恢复方案。
  • 文件夹删除必须区分删除文件夹实体和删除资源；资源默认不因移除集合关系而被物理删除。
  • 回收站需明确软删除、恢复、永久删除、子树策略和引用清理。
  • 不允许跨 Workspace 关系，不允许 Folder 循环，不允许无授权资源出现在搜索/计数/预览。

核心功能

P0： - 创建/重命名/移动/删除文件夹。 - 面包屑。 - 文件/文档/笔记区分。 - 搜索、类型筛选、排序。 - 列表/网格。 - 上传、进度、失败重试。 - PDF/图片/Markdown/表格等受支持预览。 - 详情 Inspector。 - 移动/重命名/删除/恢复。 - 空、加载、错误和权限状态。

P1： - 多选、批量移动/删除/收藏。 - 拖放上传和文件夹移动。 - 最近访问、收藏。 - 右键菜单。 - 快捷键。 - 项目资源筛选。 - 文件夹图标/封面。 - 资源关联信息。

P2： - 智能筛选视图。 - 重复文件识别。 - 文件内容全文搜索增强。 - 资源关系可视化。 - 批量整理辅助。 - 大型集合性能优化。

文件预览

建立 Preview Host + 类型 Provider。复用已有 FileDetail、ImageViewer、文件解析和处理服务。PDF 分页/按需加载；图片缩放与适配；Markdown 渲染与编辑分离；表格安全预览；未知格式提供元数据、下载和外部打开。预览不能绕过权限或将私有文件变成公开 URL。

上传队列

  • 多文件并行/限流策略。
  • 每个文件独立状态和重试。
  • 取消与失败处理。
  • 上传后进入当前目录或用户指定位置。
  • 元数据与二进制完成状态一致。
  • 支持拖入窗口、拖入目标文件夹。
  • 不因单个失败中断整个队列。

5.4 笔记与日记

  • 文件夹树、未归档、归档、回收站体验。
  • 列表密度、排序、搜索、批量选择。
  • 编辑器工具栏与内容区域层级。
  • 自动保存、保存中、保存失败状态。
  • Markdown 预览、目录、Wiki 链接、反向链接。
  • 图片和附件体验。
  • 窄屏编辑和移动端键盘遮挡。
  • 日记按时间组织，避免与普通笔记重复呈现。

5.5 文档工作区

  • 编辑/阅读模式切换。
  • 文档标题、目录、面包屑和保存状态。
  • Slash Commands、快捷键、Undo/Redo。
  • Diff/Merge、版本历史、冲突提示。
  • 图片、公式、表格、代码块、链接和 Wiki 自动补全。
  • 长文性能、滚动位置保持、编辑器焦点管理。
  • 右侧上下文和文档属性不干扰正文。

5.6 知识空间与知识图谱

  • Space 创建、选择、介绍、封面和内容组织。
  • Space 所有权、Project 关联、继承/链接关系清晰展示。
  • 图谱作用域和筛选可理解。
  • 节点/边详情、缩放、定位、搜索。
  • 大图谱布局性能、空图状态、无结果状态。
  • 区分任务依赖图与知识关系图，避免概念混淆。

5.7 项目管理

  • 项目列表、项目卡片/列表视图。
  • 项目详情与 Overview / Tasks / Knowledge。
  • 项目封面、摘要、状态、时间和关联资源。
  • 项目层级和导航。
  • 项目任务、里程碑、依赖图。
  • 归档、恢复、删除与批量操作。
  • 项目资源和知识空间关系可见但不过度复杂。

5.8 任务管理与专注

  • 列表、看板、时间线/Gantt 的一致性。
  • 任务行布局、状态操作、优先级和截止时间。
  • 快速创建、快速编辑、批量操作。
  • 任务依赖和项目归属。
  • 正向计时器与独立 Focus Timer 的语义区分。
  • 完成确认、Undo、状态反馈。
  • 大量任务虚拟化和筛选性能。

5.9 日历与提醒

  • 月/周/日/Agenda 视图一致。
  • 日期和时区处理明确。
  • 创建提醒步骤简化。
  • 重复规则和跳过实例可理解。
  • 任务与日历联动。
  • 权限、通知许可、通知失败与重试状态。
  • 移动端日期选择和触控体验。

5.10 AI Assistant / Agent

  • 对话、上下文、模型配置和审批边界清晰。
  • 消息流、工具活动、来源引用和错误状态可读。
  • 用户能理解哪些内容被提供给模型。
  • 提案、批准、应用、撤销区分明确。
  • 侧栏/浮窗不遮挡编辑内容。
  • 流式输出取消、超时和不确定发送状态清楚。
  • 不弱化现有权限过滤、Context Version、Provider Gateway、预算和 Agent 治理。

5.11 账户、设置与通知

  • 设置按任务分组，避免长页面和左右栏失衡。
  • 账户、安全、会话、工作区、同步、API/模型分区。
  • 高级信息折叠，危险操作隔离。
  • 通知分组、已读/未读、筛选和操作。
  • 同步状态区分连接、认证、绑定、Outbox、Pull、冲突。
  • 错误说明应有可执行恢复建议。

6. 统一交互规则

所有主要页面统一以下行为：

  • 单击选择、双击打开的语义只在合适的资源浏览器中采用；其他区域不得产生冲突。
  • Enter / Space / Escape / Tab / 方向键行为一致。
  • Context Menu 不能覆盖输入框和原生编辑操作。
  • Hover 不能是唯一的信息提示方式。
  • 破坏性操作必须有确认或可撤销策略。
  • 成功反馈短暂、安静；错误反馈明确、可操作。
  • 异步操作显示进度，不冻结整个页面。
  • 选中、聚焦、悬停、禁用、加载等状态必须视觉可区分。
  • 保留滚动位置和用户上下文，避免操作后无故跳回顶部。
  • 快捷键必须有帮助入口并避开系统/编辑器冲突。
  • 拖放必须有可见目标提示，并提供非拖放替代操作。

7. 响应式与跨平台

至少验证：

  • 1920×1080 / 1440×900 / 1280×800 桌面。
  • 1024px 左右窄桌面。
  • 768px 平板断点。
  • 390px / 360px 手机宽度。
  • Windows Tauri 窗口可缩放。
  • Android 竖屏与软键盘。
  • Light / Dark。
  • Comfortable / Compact 密度。

禁止仅通过 CSS 隐藏关键功能。移动端需有真实可用的替代交互。注意 safe-area、软键盘、触控尺寸、滚动容器和焦点恢复。

8. 性能与可用性目标

先建立基线，再验证改进。目标不是虚构性能数字：

  • 资源列表 1,000 项仍可流畅滚动和选择。
  • 10,000 项规模采用虚拟化或分页策略，不全量渲染 DOM。
  • 搜索输入即时反馈，查询异步且可取消/去抖。
  • 预览大型文件按需加载。
  • 详情面板不触发无关全局重渲染。
  • 页面切换尽量保留上下文。
  • 首屏分区加载，避免所有功能初始化阻塞应用。
  • 遵守真实设备能力，不在低端 Android 上强行启用昂贵效果。

9. 工程重构要求

  • 对 App.tsx、bootstrap.ts、Host 等大模块按职责审查，不机械拆分。
  • 建立 Feature Routes / Domain Hooks / Application Queries / UI components 的职责边界。
  • 资源浏览 View Model 与领域实体分离。
  • UI 不拼装跨集合的授权数据。
  • CSS 按 Token、Foundation、Component、Feature、Platform 分层。
  • 删除旧实现前先查引用、路由、测试、深链、迁移和历史数据。
  • 不保留两个长期并行的设计系统；迁移期间可以兼容，但必须有清理计划。
  • 所有新增组件具备必要测试。
  • 不为追求架构整洁而增加不必要的层。

12. 执行方式：全目标、可暂停、可恢复

12.1 不缩小范围

本任务目标是全产品升级。不得以”先做文件库”“先做设计系统”“先完成一个页面”为最终交付。阶段只是执行顺序，不是缩小任务范围。

12.2 可暂停规则

Agent 可以因以下情况暂停：

  • 上下文/Token 即将耗尽。
  • 长时间测试或构建。
  • 需要真实设备、账号或生产环境。
  • 遇到数据迁移或安全风险。
  • 依赖外部授权或用户决策。
  • 工作量需要拆分给后续会话。

暂停前必须更新：

docs/ux-upgrade/PROGRESS.md

至少包含：

  • 当前分支、HEAD、工作树状态。
  • 已完成内容与对应 Commit/文件。
  • 正在进行的工作。
  • 未完成任务及阻塞原因。
  • 测试命令、结果、日志路径。
  • 当前风险和禁止触碰事项。
  • 下一步明确的可执行任务。
  • 是否有进程仍在运行。

同时更新：

  • DECISIONS.md：设计/架构决策。
  • ISSUES.md：发现的问题和状态。
  • ACCEPTANCE.md：验收状态与证据。

不得只发聊天消息而不写入仓库检查点。

12.3 恢复规则

恢复时先读取上述检查点，检查 git 状态和进程，验证记录是否仍与当前源码一致，再继续。不可盲目重跑旧脚本覆盖日志或工件。

12.4 每个阶段的退出条件

每个阶段都必须有：

  • 实现。
  • 测试。
  • 截图或交互证据（适用时）。
  • 文档。
  • 风险说明。
  • 回滚/兼容说明（适用时）。

但阶段结束后继续下一个阶段，不等待用户重复授权，除非涉及不可逆生产操作、真实发布、密钥、付费服务或必须由用户决定的产品政策。
